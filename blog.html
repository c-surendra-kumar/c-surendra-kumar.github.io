Why Dogwhistle Detection is Harder Than It Sounds

A dogwhistle is a phrase that carries a hidden meaning — one that a general audience hears as innocuous, but an in-group recognizes as a signal. Political dogwhistles are everywhere in modern discourse, and they are deliberately designed to be deniable.

The Core Challenge

Most NLP classification tasks have a clear signal: the text either says something or it doesn't. Dogwhistles are different. The same phrase can be neutral in one context and loaded in another. "Urban voters," "inner city," "globalist" — these are not inherently problematic words, but in specific political contexts, they carry meaning that a model trained on surface form will miss.

This means standard keyword matching fails immediately. And naive fine-tuning fails too, because the training signal is too sparse and context-dependent.

Our Approach

The pipeline I built at CLIP Lab uses three stages:

  1. Transcription at scale — yt-dlp + Whisper large-v3 on an A100 GPU. We process hours of podcast audio per day.
  2. Dense retrieval — each transcript segment is embedded with OpenAI embeddings and indexed in FAISS (IndexFlatIP for cosine similarity). A query against a curated dogwhistle lexicon surfaces candidates.
  3. Contrastive classification — GPT-4 receives the candidate segment alongside a neutral paraphrase and a known dogwhistle example. It decides: is this usage coded or not?

Results

On the SALT-NLP benchmark: 98% recall and 100% precision. We validated with a JD Vance speech as a positive control and a Joe Rogan episode as a negative control. Early precision metrics were unreliable because the SALT-NLP taxonomy contains only positive examples — so we had to construct our own negatives.

What I'd Do Differently

The contrastive prompting approach works, but it's slow and expensive per segment. Next step is a lighter-weight first-pass classifier (fine-tuned BERT or similar) to reduce the number of segments sent to GPT-4. That should cut cost by ~80% with minimal recall loss.

What Makes an AI Agent Actually Useful?

I have built agents that impressed people in demos and fell apart in production. After shipping AutoCRM — a multi-agent CRM system used by actual business users — I think I understand the difference.

The Demo Problem

Demos optimize for the best case. You pick a clean input, the agent reasons beautifully, and the output looks like magic. Real users send messy inputs, ask ambiguous questions, and expect consistent behavior. Most agent frameworks are not built for that.

Three Things That Actually Matter

1. Explainability over performance. Users don't trust agents they can't understand. AutoCRM requires every agent to output a written justification alongside its action. This slows things down slightly — but it means a business user can audit and override any decision. Trust drives adoption more than accuracy does.

2. Graceful failure, not silent failure. Agents fail in weird ways. A critic agent that reviews outputs before they're finalized catches most of these — not all, but most. Design for failure from the start.

3. Configurability without code. The most valuable thing we built in AutoCRM was the Streamlit interface that lets users rewrite agent system prompts in plain language. Non-technical stakeholders could tune the agent's behavior themselves. That changed the adoption curve entirely.

The Bottom Line

A useful agent is one a non-technical user would choose to use again tomorrow. That means explainability, reliability, and control — in roughly that order.

RAG is Not Magic: Lessons from Building Three RAG Systems

Retrieval-Augmented Generation is the most overhyped and underspecified pattern in applied ML right now. Everyone says "just use RAG." Almost nobody talks about why it fails.

Failure Mode 1: Bad Chunking

How you split documents determines what gets retrieved. Fixed-size chunking loses context at boundaries. For legal documents in CaseSage, we switched to semantic chunking — splitting on paragraph and section boundaries — which improved retrieval accuracy by more than any model change we made.

Failure Mode 2: Wrong Similarity Metric

FAISS defaults to L2 distance. For most embedding models, cosine similarity works better. Switching from IndexFlatL2 to IndexFlatIP (with normalized vectors) gave us a meaningful recall improvement in the dogwhistle pipeline. This is a one-line change that's easy to overlook. 

# Wrong (L2 distance)
index = faiss.IndexFlatL2(dim)

# Right (cosine similarity via inner product on normalized vectors)
faiss.normalize_L2(embeddings)
index = faiss.IndexFlatIP(dim)

Failure Mode 3: No Evaluation

Most RAG systems ship without a retrieval evaluation suite. If you don't measure recall@k on a held-out query set, you have no idea if your changes help or hurt. RAGAS is a good starting point for end-to-end RAG evaluation. We used it for CaseSage and it caught two regressions that we would have shipped otherwise.

The Honest Summary

RAG works well when your retrieval is good, your chunks are meaningful, and you evaluate it. None of those things are given. They all require careful engineering.
